# Skill Architect

## 一、模式概览

(一) 创建模式——从需求分析到打包发布的全流程引导
(二) 审查模式——对现有技能进行结构化合规性诊断

---

## 二、模式一：创建模式

(一) 需求理解
收集用户具体使用场景、触发词和功能边界。若模式已清晰可跳过此步。

(二) 资源规划
分析每种使用场景，确定需要的资源类型：

| 类型 | 目录 | 用途 |
|------|------|------|
| 脚本 | `scripts/` | 可执行代码（同一逻辑反复重写时抽取） |
| 参考 | `references/` | 详细文档、schema、API说明 |
| 资产 | `assets/` | 模板、图标、字体等输出资源 |

依赖管理：区分硬依赖（缺了就失败）与可选依赖（增强功能），硬依赖需 `try/except` + 安装指引，可选依赖需静默降级。

(三) 初始化目录
```
skill-name/
├── SKILL.md # 必需
├── LICENSE.txt # 推荐
├── references/ # 可选
├── scripts/ # 可选
└── assets/ # 可选
```

禁止创建：`README.md`、`docs/`、`test/`、`__pycache__/`、`.env`。

(四) 编写规范

Frontmatter要求：
- `description`使用第三人称，包含触发和边界条件，≤1024字符
- `version`与CHANGELOG最新版一致
- `homepage`推荐保留

内容原则：
- 超过20行代码移至 `scripts/`
- 核心流程在正文，细节放在 `references/`
- 配置文件使用 `*.example.*` 模板提交，实际文件忽略
- 输出格式分严格模式（API/数据）和灵活模式（分析/创意）
- 工作流分顺序型和条件分支型
- 跨技能协作使用自然语言描述，禁止直接引用其他技能脚本路径

(五) 合规检查清单（10类）

| 类别 | 关键项 |
|------|--------|
| 目录结构 | SKILL.md存在、无禁止文件 |
| Frontmatter | name/description存在、第三人称、≤1024字符 |
| 行数 | ≤500行 |
| 层级 | references/scripts/assets均为扁平一级 |
| 文档一致性 | 引用的脚本/参考/资源文件实际存在 |
| 配置文件 | 模板用 `*.example.*` |
| 协作规范 | 无直接跨技能路径引用 |
| 模块化 | 独立功能解耦、无跨skill内部调用 |
| 安全审计 | 无硬编码密钥、无危险删除命令 |
| 依赖声明 | 区分开箱即用与需安装功能、脚本有try/except |

严重程度：❌严重（阻塞使用）→必须修复；⚠️警告（影响可维护性）→建议修复。

## 三、模式二：审查模式

(一) 流程
1. 指定技能路径
2. 扫描目录文件列表
3. 按10类清单逐项检查
4. 输出结构化审查报告

(二) 报告格式
```markdown
# [skill-name] 格式审查报告
**审查时间**: YYYY-MM-DD HH:MM

## 审查摘要（各类别状态与问题数表）

## 详细问题
### 严重问题（必须修复）
1. [标题] - 位置、规范、建议

### 建议优化
1. [标题] - 位置、建议
```
